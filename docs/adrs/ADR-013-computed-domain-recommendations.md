# ADR-013: Recommendation Text as Computed Properties on Domain Models

**Status:** Accepted
**Date:** 2026-02-17
**Context Domain:** Domain Modeling

## Context

The analytics system produces actionable recommendations for users: what to do about a plateau, how to fix a muscle imbalance, etc. These recommendations are displayed as text in the UI (e.g., "Consider deloading Bench Press by 10-20% and focus on form, or try a variation").

The question is where the recommendation text should be generated:
- In the service layer (services produce both data and presentation text)
- In the domain model (computed properties derive text from the model's own data)
- In the ViewModel/View layer (presentation layer formats data into text)

The DDD principle at play: domain models should own their business rules. A recommendation is a business rule ("if stalled 4+ weeks, suggest deload") expressed as text, not a presentation concern.

## Decision

Recommendation text is implemented as computed properties on domain models, not generated by services or the presentation layer.

Specifically:
- `PlateauAnalysis.recommendation: String` -- computed from `consecutiveWeeksStalled` and `exerciseName`. Rules: 4+ weeks suggests deload; 2+ weeks suggests volume increase or technique variation; otherwise, positive reinforcement.
- `MuscleImbalance.recommendation: String` -- computed from `primaryGroup`, `comparisonGroup`, `ratio`, and `severity`. Rules vary by severity (mild/moderate/severe).
- `OptimalVolumeRange.recommendation: String` -- stored as a `let` property (computed at creation time by the service) because it depends on cross-entity context not available within the model itself.

Services produce data (`PlateauAnalysis` with `consecutiveWeeksStalled`, `confidenceScore`, etc.) but do not generate presentation text. The domain model derives the recommendation from its own properties.

## Rationale

- **DDD: domain owns business rules**: The recommendation logic ("if stalled 4+ weeks, suggest deload") is a business rule, not a presentation concern. It belongs in the domain model, co-located with the data it operates on.
- **Single source of truth**: The recommendation text is always consistent with the model's data because it is derived from it via a computed property. There is no risk of the service producing a recommendation that contradicts the model's own `consecutiveWeeksStalled` value.
- **Testability**: Testing the recommendation is a simple unit test: create a `PlateauAnalysis` with `consecutiveWeeksStalled = 5`, assert on `.recommendation`. No service instantiation needed.
- **No duplication**: If the recommendation logic lived in the service, every consumer of `PlateauAnalysis` would need to either call the service for the text or duplicate the logic.
- **Simplicity**: Computed properties require no additional state, no caching, and no initialization complexity.

## Alternatives Considered

- **Service generates recommendation text**: Rejected because it separates the business rule from the data it acts on. The service would need to hold the same domain knowledge as the model (how many weeks = deload), creating duplication and risk of inconsistency.
- **ViewModel/View formats recommendations**: Rejected because the recommendation logic ("4+ weeks = deload") is a domain rule, not a UI formatting concern. Putting it in the View layer would mean iOS and Watch apps must duplicate the logic.
- **Stored property set by service**: Rejected for `PlateauAnalysis` and `MuscleImbalance` because the recommendation is entirely derivable from the model's own properties. Using a stored property would allow the text to be inconsistent with the data (e.g., recommendation says "2 weeks stalled" but `consecutiveWeeksStalled` is 5). Exception: `OptimalVolumeRange.recommendation` is stored because it depends on cross-entity context.
- **Separate Recommendation model**: Rejected as unnecessary indirection. The recommendation is a property of the analysis, not a standalone entity.

## Consequences

### Positive
- Domain model is self-describing (carry data + derived interpretation together)
- Business rules are co-located with the data they operate on
- Easy to test (create model, check computed property)
- No risk of recommendation text contradicting model data
- Services remain focused on computation (producing data, not text)

### Negative / Trade-offs
- Computed properties cannot access external context (e.g., exercise database, user preferences). If a future recommendation needs external data, it must be refactored to a stored property or a separate method.
- Recommendation text is in English only. Localization would require refactoring to use `NSLocalizedString` or similar, which computed properties can do but at the cost of added complexity.
- `OptimalVolumeRange.recommendation` breaks the pattern by using a stored `let` property (because it needs cross-entity context). This inconsistency may confuse developers.

### Neutral
- The architecture doc explicitly calls out this pattern with comments like "DDD: domain model owns its business rules, services produce data not presentation"
- Both `PlateauAnalysis.recommendation` and `MuscleImbalance.recommendation` are `var` computed properties, not `let` stored properties

## Implementation Notes

- **PlateauAnalysis.recommendation** (`Shared/Models/Domain/Analytics/PlateauAnalysis.swift`):
  ```swift
  public var recommendation: String {
      guard let name = exerciseName else { return "" }
      if consecutiveWeeksStalled >= 4 {
          return "Consider deloading \(name) by 10-20% and focus on form, or try a variation."
      } else if consecutiveWeeksStalled >= 2 {
          return "Try increasing volume by 5-10% or adding a technique like drop sets for \(name)."
      } else {
          return "Progress is on track for \(name). Keep pushing!"
      }
  }
  ```
- **MuscleImbalance.recommendation** (`Shared/Models/Domain/Analytics/MuscleBalance.swift`):
  ```swift
  public var recommendation: String {
      switch severity {
      case .severe:
          return "Significantly reduce \(primaryGroup.rawValue) volume and increase \(comparisonGroup.rawValue) by 30-40%..."
      case .moderate:
          return "Increase \(comparisonGroup.rawValue) volume by 20-30%..."
      case .mild:
          return "Consider adding 1-2 more sets for \(comparisonGroup.rawValue)..."
      }
  }
  ```
- **Service comment pattern**: Services contain comments like `// Note: recommendation is a computed property on PlateauAnalysis (DDD: domain owns its rules)` to explain why the service does not generate recommendation text.
